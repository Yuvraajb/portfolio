# Yuvraaj Bhatter — personal website

A personal site with a homepage stream of long-form posts plus dedicated
Bookshelf, GitHub, and About pages — dark, flat, a little toy-like (chunky
outlines, hard "sticker" drop-shadows, no blur/glow, one fixed palette).
It's generated by plain Node.js with **zero npm dependencies**: markdown
and JSON files in, static HTML out.

## Quick start

```
npm run build   # generate the site into public/
npm run dev     # build, then serve it at http://localhost:4000
```

Open http://localhost:4000 and you should see the site. Every page,
including the RSS feed, is a plain static file under `public/` after
`npm run build` — you can deploy that folder to literally any static host
(GitHub Pages, Netlify, Vercel, S3, nginx, whatever).

`public/` is git-ignored on purpose — it's generated output, not something
you hand-edit. Re-run `npm run build` any time content changes, or set up
the GitHub Actions workflow below to do it automatically.

## Project layout

```
content/
  site.json            Your name, bio, tagline, nav links, social links
  posts/*.md            Long-form blog posts you write locally
  blog-feed.json        Posts synced from an RSS feed (generated -- see below)
  bookshelf.json        What you're reading / have read / want to read
  github-activity.json  Recently-pushed public repos (generated -- see below)
  about.md              The "About" page (rendered as a terminal window)
assets/
  css/style.css     All the visual design lives in this one file
  images/           Avatar, favicon
scripts/
  build.js          Reads content/, writes public/
  server.js         Zero-dependency static file server for local preview
  markdown.js       The ~150-line markdown-to-HTML converter
  frontmatter.js    Parses the `--- key: value ---` header on .md files
  sync-goodreads.js Pulls your public Goodreads shelves into bookshelf.json
  sync-blog.js      Pulls posts from any RSS/Atom feed into blog-feed.json
  sync-github.js    Pulls recent public repo activity into github-activity.json
```

## Updating content

**This is the whole point: editing content should never require touching
code.**

### Add a blog post

Create `content/posts/YYYY-MM-DD-your-slug.md`:

```markdown
---
title: Your Post Title
tags: [optional, tags]
---

Your post body in **markdown**. Supports headings, lists, links,
`inline code`, fenced code blocks, blockquotes, and images.
```

The filename's date becomes the post date and the URL is
`/blog/your-slug/`, unless you override either with `date:` or `slug:` in
the frontmatter. Run `npm run build` and it shows up on the homepage
stream, `/blog/`, and `/feed.xml` automatically.

**Or don't write markdown files at all** — see "The Blog: local posts or a
live feed sync" below to have posts appear here automatically when you
publish somewhere else instead.

### Update your bio, tagline, nav, or social links

Edit `content/site.json`. It's plain JSON — `name`, `tagline`, `bio`,
`avatar`, `email`, `social` (array of `{label, url, icon}` — icons
available: `github`, `twitter`, `book`, `rss`), and `nav`.

### Update the About page

Edit `content/about.md` directly — plain markdown, no frontmatter
required. `## Headings` render as `[ BRACKETED HUD LABELS ]` and list
items get a `>` prompt marker, to match the terminal-window styling that
page gets — see "Change the look" below if you want to adjust that.

There's no hand-edited "Now" page — see "GitHub activity" below for what
replaced it.

### Update your avatar

Replace `assets/images/avatar-placeholder.svg` with a real photo (any
image format works — update the `avatar` path in `content/site.json` to
match, e.g. `/assets/images/me.jpg`).

### Change the look

Everything visual is in `assets/css/style.css` — colors are CSS custom
properties at the top of the file (`--bg`, `--ink`, `--purple`, `--pink`,
`--teal`, `--yellow`, `--orange`, `--green`). One fixed dark palette, no
theme switching, no background texture, no glow/blur effects — just flat
color, chunky borders, and hard-edged "sticker" drop-shadows.

## Projects: replaces a hand-maintained "Now" page

Instead of a manually-edited "what I'm up to" page, `/projects/` and the
homepage sidebar show recently-pushed public repositories, pulled straight
from a GitHub profile via the public REST API — no token, no auth, so it
can only ever see public repos (which is also exactly what should be on a
public website).

**Status for this site:** `content/github-activity.json` already holds
real data for `github.com/yuvraajb` (fetched directly, not guessed) —
`portfolio`, `wc26-intelligence`, `blind75`, and a few others, each with
its description, language, and last-pushed date. Nothing left to verify
here, unlike the blog/bookshelf sections below.

To re-sync manually:

```
node scripts/sync-github.js yuvraajb
npm run build
```

Each entry shows the repo name, description, primary language, and
whether it looks like it was newly created or just updated (a repo whose
`created_at` and `pushed_at` are the same day is labeled "Created", else
"Updated"). Forks, archived repos, and the special profile-readme repo
(the one matching your username) are excluded automatically. Capped to
the 6 most recently pushed — change `MAX_REPOS` in `scripts/sync-github.js`
for more or fewer.

**Automating it:** `.github/workflows/website-sync-github.yml` already
runs this nightly (~midnight IST / 18:30 UTC) and commits any changes —
**no GitHub configuration needed.** A username isn't a secret, so it's
hardcoded in the workflow as `DEFAULT_GITHUB_USERNAME`. To point it at a
different profile without editing the workflow file, add a repository
variable named `SYNC_GITHUB_USERNAME` (Settings → Secrets and variables →
Actions → Variables) — it overrides the hardcoded default. (Note: it's
`SYNC_GITHUB_USERNAME`, not `GITHUB_SYNC_USERNAME` — GitHub Actions
reserves the `GITHUB_` prefix for its own variables and will reject one
you try to create with that prefix.)

**If you'd rather not sync this at all:** delete
`content/github-activity.json` and don't run the sync script — `build.js`
checks whether that file exists and simply skips the `/projects/` page and
widget if it's missing.

## The Blog: local posts or a live feed sync

**Status for this site:** `content/site.json`'s `externalBlog.feedUrl` is
set to `https://yuvraajbhatter1.substack.com/feed` — a guess based on the
Substack profile handle (`substack.com/@yuvraajbhatter1`), since a Substack
profile URL doesn't always match the newsletter's own subdomain, and this
was configured from an environment that couldn't reach substack.com to
confirm it. **Verify it**: open that feed URL in a browser — if it returns
XML with your posts, it's right; if it 404s, open your actual newsletter
and check its URL, or look for an RSS link in its footer, then update
`feedUrl` (and re-run the sync below).

You don't have to hand-edit a markdown file every time you want to publish.
`scripts/sync-blog.js` pulls posts from **any RSS or Atom feed** and turns
them into pages here automatically — it's not tied to one platform. That
covers basically every blogging tool that exists, because they all expose
a feed:

```
node scripts/sync-blog.js https://yourname.substack.com/feed Substack
npm run build
```

- **Substack:** `https://<yourname>.substack.com/feed`
- **Medium (personal):** `https://medium.com/feed/@<yourname>`
- **Medium (publication):** `https://medium.com/feed/<publication-name>`
- **WordPress:** `https://yoursite.com/feed/` (on by default)
- **Ghost:** `https://yoursite.com/rss/` (on by default)
- **Blogger:** `https://yourname.blogspot.com/feeds/posts/default`
- **Dev.to:** `https://dev.to/feed/<username>`
- **Hashnode:** `https://<yourname>.hashnode.dev/rss.xml`
- **Notion-as-a-blog tools** (Super, Potion, etc.): check the tool's
  settings for an RSS/feed URL — most of them generate one

If your platform isn't in that list, look for "RSS" or "feed" in its
settings/footer, or try appending `/feed`, `/rss`, or `/rss.xml` to your
blog's URL — one of those almost always works. The second argument to the
script (`Substack` above) is just the label shown in the "via ___" badge —
set it to whatever your platform is actually called.

Running the sync writes `content/blog-feed.json`, which `build.js` merges
into the homepage stream, `/blog/`, and the RSS feed right alongside your
local `content/posts/*.md` files — no conflict between the two, a post can
come from either place. Each synced post gets:

- a **"via Substack"** (or Medium) badge in the stream, so it's clear it's
  syndicated, not written directly on this site
- an **"Originally published on Substack ↗"** link at the top of the post
  pointing at the canonical URL
- a `<link rel="canonical">` tag pointing at that same URL, so search
  engines credit the original post, not the mirror here

If a local markdown post and a synced post ever end up with the same slug,
the local file wins (yours is assumed more authoritative than the feed).

Script content is sanitized on the way in (script tags, inline event
handlers, and `javascript:` links are stripped) — a lightweight safety net
since this is HTML from a third-party platform being embedded in your own
site, not something a full HTML parser needs to referee.

**Automating it:** `.github/workflows/website-sync-blog.yml` already runs
this nightly (~midnight IST / 18:30 UTC) and commits any changes — **no
GitHub configuration needed.** A feed URL isn't a secret, so it's
hardcoded in the workflow as `DEFAULT_BLOG_FEED_URL`. If you ever want to
change the feed without editing the workflow file, add a repository
variable named `BLOG_FEED_URL` (Settings → Secrets and variables →
Actions → Variables) — it overrides the hardcoded default — and optionally
`BLOG_PROVIDER` (e.g. `Substack` or `Medium`) to control the badge text.

**If you don't want this at all:** just keep writing `content/posts/*.md`
files by hand and never run the sync script — `blog-feed.json` simply won't
exist and nothing changes.

## The Bookshelf: manual editing or Goodreads sync

**Status for this site:** the real Goodreads profile
(`goodreads.com/user/show/165341026-yuvraaj-bhatter`, user ID `165341026`)
is linked in `content/site.json`'s social links and in `about.md`, but
`content/bookshelf.json` still holds placeholder books — the sync below
was attempted from an environment that can't reach goodreads.com, so it
never ran. Run it from a normal machine or let CI do it (see "Automating
it" below) to pull your real shelves.

`content/bookshelf.json` is a plain array of books:

```json
{
  "title": "Book Title",
  "author": "Author Name",
  "status": "currently-reading",
  "cover": "https://covers.openlibrary.org/b/isbn/ISBN-M.jpg",
  "rating": 5,
  "dateFinished": "2026-01-15",
  "link": "https://www.goodreads.com/book/show/12345"
}
```

`status` is one of `currently-reading`, `read`, or `want-to-read`. `rating`
(1–5) and `dateFinished` are only meaningful for `read`. You can edit this
file by hand any time and re-run `npm run build`.

`/bookshelf/` renders these as a grid of covers grouped by status, each
with a colored border, title, author, star rating, and finish date. Click
a cover to jump to that book's Goodreads page. The homepage sidebar shows
a compact list of whatever's in `currently-reading`.

### Connecting it to your real Goodreads — yes, this is possible

Goodreads **retired its public developer API in 2020** and hasn't issued
new API keys since, so there's no clean "official" way to pull your data
anymore. The workaround nearly everyone uses is that Goodreads still
serves a public **RSS feed per shelf**, which doesn't require a key:

```
https://www.goodreads.com/review/list_rss/<your_user_id>?shelf=<shelf_name>
```

`scripts/sync-goodreads.js` fetches your `currently-reading`, `read`, and
`to-read` shelves from that endpoint and rewrites `content/bookshelf.json`
for you. To use it:

1. **Make your profile public.** On Goodreads: Settings → Profile →
   make sure your profile and shelves aren't private, or the RSS feeds
   will come back empty.
2. **Find your user ID.** Open your Goodreads profile — the URL looks like
   `https://www.goodreads.com/user/show/12345678-your-name`. `12345678` is
   your user ID.
3. **Run the sync:**
   ```
   node scripts/sync-goodreads.js 12345678
   npm run build
   ```

That's it — `content/bookshelf.json` is regenerated from your real shelves
(capped at 15 recent "read" books and 10 recent "want to read" books, so
the page doesn't turn into your entire library; edit the `limit` values in
`scripts/sync-goodreads.js` if you want more or fewer).

**Automating it:** `.github/workflows/website-sync-goodreads.yml` (at the
repo root) already runs this sync nightly (~midnight IST / 18:30 UTC) and
commits any changes — **no GitHub configuration needed.** A Goodreads user
ID isn't a secret (it's the number in your public profile URL), so it's
hardcoded in the workflow as `DEFAULT_GOODREADS_USER_ID: '165341026'`. To
point it at a different account later without editing the workflow file,
add a repository variable named `GOODREADS_USER_ID` (Settings → Secrets
and variables → Actions → Variables) — it overrides the hardcoded default.

If Goodreads ever changes its RSS format (they've done it before), this is
the one script that would need updating — everything else on the site is
unaffected.

**If you'd rather not touch Goodreads at all:** just hand-edit
`content/bookshelf.json`. It's simpler, more reliable, and honestly what I'd
recommend unless you really want the automation.

## Hosting / deployment

Four GitHub Actions workflows live at the **repo root** (not inside this
`website/` folder, since GitHub only reads workflows from
`.github/workflows/` at the top level):

- **`website-build-check.yml`** — runs `npm run build` on every push and
  PR that touches `website/**`, so a broken build shows up as a failed
  check instead of silently shipping.
- **`website-deploy.yml`** — builds the site and deploys `public/` to
  GitHub Pages whenever `website/**` changes on `main`.
- **`website-sync-goodreads.yml`** — the scheduled Goodreads sync
  described above.
- **`website-sync-blog.yml`** — the scheduled RSS feed sync described above.

Both sync workflows commit straight to whatever branch they run on. On
GitHub Pages, that push triggers `website-deploy.yml` directly. **On
Vercel** (see below), Vercel's own Git integration watches the branch and
rebuilds on every push — including the sync workflows' commits — so no
extra wiring is needed there either way. Either way, publishing a new post
or finishing a book on Goodreads reaches your live site within a day with
zero manual steps, since both sync workflows already have real (or
best-guess, for the blog) values hardcoded rather than waiting on repo
configuration — see "Automating it" in each section above.

### Deploying on Vercel

This repo includes `website/vercel.json` (`buildCommand: npm run build`,
`outputDirectory: public`), so Vercel needs almost no manual setup:

1. [Import the repo into Vercel](https://vercel.com/new).
2. Set **Root Directory** to `website` — this is the one setting Vercel
   can't infer, since the site lives in a subfolder of this repo, not the
   repo root.
3. Framework Preset: "Other" (there's no framework here to detect).
4. Deploy. Every push to whatever branch you connect — including the
   nightly sync workflows' commits — triggers a new deployment
   automatically.

Nothing about the sync workflows changes for Vercel: they still run on
GitHub's infrastructure (not Vercel's), commit straight to the repo, and
Vercel just reacts to the push like any other commit.

### Deploying on GitHub Pages instead

Two things first, since GitHub Pages needs slightly more manual setup
than Vercel:

1. **Enable GitHub Pages** for this repository: Settings → Pages → Source
   → "GitHub Actions". This is a one-time manual setting; it can't be
   turned on from a workflow file.
2. **Check your default branch.** This repo's current default branch is
   not `main` (it's a session branch created for this task). The deploy
   workflow triggers on pushes to `main` specifically — either create a
   `main` branch as your long-term default, or edit the `branches:` line
   in `.github/workflows/website-deploy.yml` to match whatever branch you
   actually want to deploy from.

Other static hosts (Netlify, Cloudflare Pages) work the same way as
Vercel: point their build command at `cd website && npm run build` and
their publish directory at `website/public`.

## Why no framework

See [the post about it](content/posts/2026-03-20-static-site-no-framework.md)
once the site is live, or just: this site is small enough that a hand-rolled
~500-line generator is easier to fully understand and maintain than adopting
a framework's release cycle, dependency tree, and breaking changes for a
handful of markdown files.
